# Working in this repo

This is the live `~/.claude` config — edits to skills take effect in running Claude Code sessions immediately. That immediacy is why the live directory is versioned in place rather than a clean repo being synced in, and its price is a working tree holding runtime state, secrets, and foreign checkouts: the allowlist `.gitignore`, the `git ls-files` file lists, and the hand-named test suites all descend from that one decision — weaken none of them without revisiting it.

Nothing here auto-loads. `~/.claude/CLAUDE.md` is global user memory, loaded into every session in every project, so only universal personal preferences belong in it and it cannot import these notes without taxing every project. Agent-facing repo knowledge therefore lives in `references/`, and the skills that need a convention point at the file by path.

- `just check` is the check suite: it typechecks every F# project, runs the test suites, and lints shell scripts. Lefthook runs it pre-commit when a `*.fs`/`*.fsproj` is staged, and `just shell` alone when only a `*.sh` is; GitHub Actions runs `just check` inside the devcontainer on push and PR — add checks to the `justfile` rather than to the workflow, or the two drift. F# has no linter, and markdown and skills have no automated validation, so for those it stays reading the diff and running the skill.
- Tool versions are pinned in `.devcontainer/devcontainer.json` and nowhere else: CI runs `just check` inside that container, so bump a version there, never in the workflow. Add tools as devcontainer features, preferring official → the tool's own maintainers → [mine](https://github.com/NicoVIII/devcontainer-features/tree/main/src) → devcontainers-extra → (tie) unknown third-party or a manual install. Anthropic's `claude-code` feature exposes no version option, so it alone tracks latest; `claude-mount` shares the host's `~/.claude` read-write, credentials included. `devcontainer-lock.json` pins the feature implementations by digest — commit the refreshed lock whenever you change a feature.
- Tests are integration-first: the helpers are thin layers over files and processes, so drive the built binary against a throwaway root (`bin/skill-refiner.tests/Harness.fs`) instead of unit-testing the layers. Unit tests are for paths complex enough to earn them — the log's parser does, a `File.ReadAllText` wrapper doesn't. Mark arrange/act/assert, keep setup in named harness helpers so the body shows only what the test is about, and leave the commit references alone: a test citing one is pinning that regression. Nothing gh-facing is covered — `lib/gh`'s `run` hardcodes `Process.Start "gh"` with no seam to fake — so `gather` has no suite at all and `survey`'s reaches only `Bumps`, the one pure module. `just test` names each suite by hand; a new one has to be added there.
- The `just check` file lists come from `git ls-files` (`*.fsproj`, `*.sh`), not a glob: `~/.claude` holds untracked state and foreign checkouts that a `**` walk would wander into. A new helper is therefore checked as soon as it is staged, and needs no registration anywhere — except a test suite, which `just test` names by hand, and a project nested deeper than `bin/*`, `lib/*` or `skills/*/scripts/*`, whose level `.github/dependabot.yml` has to list before NuGet bumps reach it.
- This repo is public (`github.com/NicoVIII/claude-config`) and meant to be usable by others, though its primary goal is versioning my own setup. The README addresses third-party users too; first-person voice in skills ("my repos") is fine — it resolves to whoever runs them.
- No ADRs. Decision rationale lives in commit messages; a decision that must constrain future work (especially "we tried/considered X — don't") gets a one-line guardrail here or in the relevant SKILL.md, citing its commit for the full story.
- `.gitignore` is an allowlist by design: secrets and runtime state live in this directory, so everything is ignored by default. Never loosen the catch-all. A new *top-level* path needs an explicit `!/...` entry; anything beneath an already-allowed directory like `skills/` or `bin/` is tracked without one.
- One home per fact across README, these reference files, and SKILL.mds: what a human acts on before a session exists (setup, model choice) → README; what an agent acts on → `references/` or the relevant SKILL.md. Several skills read named README sections at run time (`author-skill` → Skills + Workflows; `skill-retro` and `pick-model` → the maturity table), so before moving, renaming, or cutting doc sections, grep `skills/` and `references/` for references (af2f8fb).
