# Working in this repo

This is the live `~/.claude` config — edits to skills take effect in running Claude Code sessions immediately.

- `just check` is the check suite: it typechecks every F# project, runs the test suites, and lints shell scripts. Lefthook runs it pre-commit when a `*.fs`/`*.fsproj` is staged, and `just shell` alone when only a `*.sh` is; GitHub Actions runs `just check` inside the devcontainer on push and PR — add checks to the `justfile` rather than to the workflow, or the two drift. F# has no linter, and markdown and skills have no automated validation, so for those it stays reading the diff and running the skill.
- Tool versions are pinned in `.devcontainer/devcontainer.json` and nowhere else: CI runs `just check` inside that container, so bump a version there, never in the workflow. Add tools as devcontainer features, preferring official → the tool's own maintainers → [mine](https://github.com/NicoVIII/devcontainer-features/tree/main/src) → devcontainers-extra → (tie) unknown third-party or a manual install. Anthropic's `claude-code` feature exposes no version option, so it alone tracks latest; `claude-mount` shares the host's `~/.claude` read-write, credentials included. `devcontainer-lock.json` pins the feature implementations by digest — commit the refreshed lock whenever you change a feature.
- Tests are integration-first: the helpers are thin layers over files and processes, so drive the built binary against a throwaway root (`bin/runlog.tests/Harness.fs`) instead of unit-testing the layers. Unit tests are for paths complex enough to earn them — `parseVerdict` does, a `File.ReadAllText` wrapper doesn't. Mark arrange/act/assert, keep setup in named harness helpers so the body shows only what the test is about, and leave the commit references alone: a test citing one is pinning that regression. Nothing gh-facing is covered — `bin/gh`'s `run` hardcodes `Process.Start "gh"` with no seam to fake — so `gather` has no suite at all and `survey`'s reaches only `Bumps`, the one pure module. `just test` names each suite by hand; a new one has to be added there.
- The `just check` file lists come from `git ls-files` (`*.fsproj`, `*.sh`), not a glob: `~/.claude` holds untracked state and foreign checkouts that a `**` walk would wander into. A new helper is therefore checked as soon as it is staged, and needs no registration anywhere — except a test suite, which `just test` names by hand.
- This repo is public (`github.com/NicoVIII/claude-config`) and meant to be usable by others, though its primary goal is versioning my own setup. The README addresses third-party users too; first-person voice in skills ("my repos") is fine — it resolves to whoever runs them.
- No ADRs. Decision rationale lives in commit messages; a decision that must constrain future work (especially "we tried/considered X — don't") gets a one-line guardrail here or in the relevant SKILL.md, citing its commit for the full story.
- `.gitignore` is an allowlist by design: secrets and runtime state live in this directory, so everything is ignored by default. Never loosen the catch-all. A new *top-level* path needs an explicit `!/...` entry; anything beneath an already-allowed directory like `skills/` or `bin/` is tracked without one.
- `CLAUDE.md` here is global user memory, loaded into every session in every project — only universal personal preferences belong in it, and every word has token cost everywhere. Repo-scoped guardrails go in this file instead. This file loads into every session in this repo, so it is held to the same bar — by review, not by a tool, since `runlog ratio` only measures skills. Depth that only some sessions need goes in `references/`, leaving a one-line pointer here.
- One home per fact across README, this file, and SKILL.mds: what a human acts on before a session exists (setup, model choice) → README; what an agent acts on → this file or the relevant SKILL.md. Several skills read named README sections at run time (`author-skill` → Skills + Workflows; `skill-retro` and `pick-model` → the maturity table), so before moving, renaming, or cutting doc sections, grep `skills/` and this file for references (af2f8fb).
- Write and refine skills with the most capable model available (currently Fable, otherwise Opus), even when the skill's suggested execution model is Sonnet: skill text is written once but steers every future run, and the hard part is anticipating how a smaller executor will misread it. Mechanical edits (typos, renames) don't need this. Deliberate exception: `skill-retro`'s suggested *run* model stays Opus — its edits are anchored to observed friction rather than open-ended authoring, and it runs after every skill iteration, so cost weighs heavier there (1468685).
- Before writing an executable helper for a skill — or deciding whether it should be a shell script or an F# project, and whether it belongs in `bin/` or beside one SKILL.md — read [`references/helpers.md`](references/helpers.md). That is the one place those rules live.
- `skills/*/SKILL.md` frontmatter must start at byte 0 (nothing above the first `---`, or it silently fails to parse). The `description` field is the model's only trigger signal — keep it rich in trigger phrases.
- Skills below 🟢 Usable in the README maturity table (🚧 WIP, 🧪 Experimental) end with a one-line feedback footer asking the executing agent to surface friction. Add it (identical wording, copied from an existing 🧪 Experimental skill — Usable ones no longer carry it) to every new skill; remove it when a skill graduates to Usable — mature skills are daily drivers where the footer is noise, and `/skill-retro` on demand covers them. `/skill-retro` turns the surfaced friction into skill edits. A `SKILL.md` ends with that footer and nothing after it — upstream attributions belong in the README's credits line, since a `SKILL.md` loads into context on every invocation.
