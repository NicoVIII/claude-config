# Working in this repo

This is the live `~/.claude` config — edits to skills take effect in running Claude Code sessions immediately. That immediacy is why the live directory is versioned in place rather than a clean repo being synced in, and its price is a working tree holding runtime state, secrets, and foreign checkouts: the allowlist `.gitignore`, the `git ls-files` file lists, and the hand-named test suites all descend from that one decision — weaken none of them without revisiting it.

This file loads only in sessions started inside this repo: it is the repo's *project* memory, where the root `CLAUDE.md` is global user memory, loaded into every session in every project, and so cannot carry or import these notes without taxing every project. It is a `CLAUDE.md` and not the `AGENTS.md` my other repos use because Claude Code falls back to `AGENTS.md` only in a project with no `CLAUDE.md` of its own, and this one has the global file at its root (tested on 2.1.322: `.claude/AGENTS.md` here did not load, this did, and neither loads from another directory). A skill running from another repo gets none of this for free and names this file by path. `references/` is not loaded anywhere: it holds what skills need across repos, and they point at each file by path.

- A commit's check suite is what `lefthook.yml` runs for the staged paths: `just typecheck test` when a `*.fs`/`*.fsproj` is staged, `just shell` when a `*.sh` is, `just contract` when an F# source, a tool wrapper, `lib/cli-stub.sh` or anything in a `*.contract/` suite is, and nothing otherwise. A commit touching only markdown and skills has no automated checks — review the diff and commit; don't run `just check`, whose `just shell` and `just contract` fail wherever `shfmt` or `scrut` isn't installed (everywhere but the devcontainer) and would block a commit they have nothing to say about. `just check` runs all four and is what GitHub Actions runs inside the devcontainer on push and PR — add checks to the `justfile` rather than to the workflow, or the two drift.
- Tool versions are pinned in `.devcontainer/devcontainer.json` and nowhere else: CI runs `just check` inside that container, so bump a version there, never in the workflow. Add tools as devcontainer features, preferring official → the tool's own maintainers → [mine](https://github.com/NicoVIII/devcontainer-features/tree/main/src) → devcontainers-extra → (tie) unknown third-party or a manual install. Anthropic's `claude-code` feature exposes no version option, so it alone tracks latest; `claude-mount` shares the host's `~/.claude` read-write, credentials included. `devcontainer-lock.json` pins the feature implementations by digest — commit the refreshed lock whenever you change a feature.
- Tests are integration-first: the helpers are thin layers over files and processes, so drive the built binary against a throwaway root (`bin/skill-refiner.tests/Harness.fs`) instead of unit-testing the layers. Unit tests are for paths complex enough to earn them — the log's parser does, a `File.ReadAllText` wrapper doesn't. Mark arrange/act/assert, keep setup in named harness helpers so the body shows only what the test is about, and leave the commit references alone: a test citing one is pinning that regression. In-process, nothing gh-facing is covered — `lib/gh`'s `run` hardcodes `Process.Start "gh"` with no seam to fake — so `survey`'s Expecto suite reaches only `Bumps`, the one pure module. The seam for external commands is `PATH` instead: a `<tool>.contract/` Scrut suite beside the helper runs it through its wrapper against `lib/cli-stub.sh`, symlinked as `gh`, which answers only the calls a scenario's `calls` file lists, so a changed flag fails too; `gather`, `survey` and `failing-log` are covered this way (#7). The stub runs no `--jq` filter, so a fixture holds what gh would have printed after it. `skill-refiner` has a contract suite too, for the output the skills quote whole; it calls no stubbed command, and because the wrapper's binary sits in the real config tree, the suite owns only the `.claude/skills` of a throwaway session repo — a skill name its fixture lacks falls through to the real `skills/`, where a `log` would append to a real `HISTORY.md`. A helper that only needs HTTP has a better seam than `PATH` and does not shell out to `curl` to reach the stub: `feature-probe` takes its `HttpMessageHandler` as an argument, and its Expecto suite fakes that one, answering only the requests a test lists, so a changed URL or a dropped header fails the same way — at the price of `Program.fs`, kept to the printing, going unexercised. `dependabot-schema` fetches in-process too, without that seam, and has no suite. `just test` and `just contract` name each suite by hand; a new one has to be added there.
- The `just check` file lists come from `git ls-files` (`*.fsproj`, `*.sh`), not a glob: `~/.claude` holds untracked state and foreign checkouts that a `**` walk would wander into. A new helper is therefore checked as soon as it is staged — stage it before running `just check`, which otherwise passes without having seen it — and needs no registration anywhere except a test suite, which `just test` names by hand, and a project nested deeper than `bin/*`, `lib/*` or `skills/*/scripts/*`, whose level `.github/dependabot.yml` has to list before NuGet bumps reach it.
- This repo is public (`github.com/NicoVIII/claude-config`) and meant to be usable by others, though its primary goal is versioning my own setup. The README addresses third-party users too; first-person voice in skills ("my repos") is fine — it resolves to whoever runs them.
- No ADRs for how this config is built. Its decision rationale lives in commit messages; a decision that must constrain future work (especially "we tried/considered X — don't") gets a one-line guardrail here or in the relevant SKILL.md, citing its commit for the full story (b22d4e3). `standards/` is the exception, because neither reason holds there: a standard's rule was rarely decided in a diff of this repo, and the reader of its rationale is me re-reading it, not an agent that would need it loaded. A rule there gets a record in `standards/decisions/` when it passes the test in `standards/README.md` — which is about the standards' content; how `standards/` itself is built is still commit-message material.
- `.gitignore` is an allowlist by design: secrets and runtime state live in this directory, so everything is ignored by default. Never loosen the catch-all. A new *top-level* path needs an explicit `!/...` entry, and so does a new file in `.claude/`, which is re-ignored wholesale; anything beneath an already-allowed directory like `skills/` or `bin/` is tracked without one.
- One home per fact across README, this file, `references/`, and SKILL.mds: what a human acts on before a session exists (setup, model choice) → README; why the config is built this way → `docs/design.md`, which the README only summarises; what an agent working on this repo acts on → here; what a skill needs wherever it runs → `references/` or the relevant SKILL.md; how I do a kind of work in any repo → `standards/`, whose rules for writing one are in its README. A standard reaches a session only through its line in the root `CLAUDE.md`, so a new file there needs that line, naming the work it is read before. Several skills read named README sections at run time (`author-skill` → Skills + Workflows; `skill-retro` and `pick-model` → the maturity table), so before moving, renaming, or cutting doc sections, grep `skills/` and `references/` for references (af2f8fb). `bin/skill-refiner/ProjectSkillsReadme.md` has a fourth audience — a stranger who found a `.claude/skills/` folder in their own repo — so it explains what is there and what wrote it, and carries no instruction for maintaining skills: what it seeds must stay *usable* without this config, not maintainable without it (9056afe).
